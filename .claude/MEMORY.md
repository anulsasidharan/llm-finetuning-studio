## ARCHITECTURE DECISIONS (DO NOT REVISIT)
- Frontend: Next.js 14 App Router only — never Pages Router
- State: TanStack Query (server) + Zustand (client) + React Hook Form + Zod (forms)
- Python package manager: uv — never bare pip
- DB ORM: SQLAlchemy 2 async — never sync sessions
- Storage: MinIO in dev, S3 in production — client in core/storage.py
- Task queue: Celery with Redis broker — 3 queues: training, export, default
- Logging: structlog JSON — never print()
- Config: pydantic-settings Settings class — never os.environ directly
- Auth: JWT (python-jose) + bcrypt (passlib) — self-contained, no external auth
- bcrypt MUST stay pinned to 4.0.1 in apps/backend/requirements.txt — passlib 1.7.4 (unmaintained) is incompatible with bcrypt>=4.1's stricter 72-byte enforcement (raises ValueError during passlib's internal self-test); do not bump bcrypt without also replacing passlib
- tests/conftest.py's `client` TestClient fixture MUST stay session-scoped, not function-scoped — the async SQLAlchemy engine/pool in core/database.py is a process-wide singleton; a function-scoped fixture gives each test its own asyncio event loop, and connections leak across loops, crashing on Windows+asyncpg with "Event loop is closed". One shared loop for the whole pytest session avoids this entirely
- DB-touching backend tests need DATABASE_URL/DATABASE_URL_SYNC overridden to localhost:5433 (not the .env default of docker-internal host "postgres:5432") when run locally outside Docker via `uv run pytest` — exactly mirrors what .github/workflows/ci.yml's backend-test job already does with its own ephemeral postgres service; no code change needed, just env vars at invocation time
- AppException subclasses (ConflictError, UnauthorizedError, etc. from core/exceptions.py) only produce their declared status_code because main.py registers an `@app.exception_handler(AppException)` → JSONResponse handler; without it they'd bubble up as unhandled 500s
- Model catalog + GPU pricing are DB-backed tables (model_catalog, gpu_pricing — added PHASE1-WEEK2-013), NOT static Python config — chosen because GET /models/catalog and GET /gpu/pricing are planned as real queryable routes. Both are global reference tables (no user_id FK). Seeded idempotently via apps/backend/scripts/seed_data.py using `postgresql.insert(...).on_conflict_do_update(...)` upserts
- Standalone scripts under apps/backend/scripts/ that import `core`/`models` need a `sys.path.insert(0, parent)` bootstrap at the top of the file — `uv run python scripts/foo.py` sets sys.path[0] to the script's own directory, not the invocation cwd, so bare `from core...` imports 404 otherwise (mirrors why alembic.ini has `prepend_sys_path = .`). ruff.toml's `"scripts/*"` per-file-ignore includes `E402` to allow the bootstrap to precede other imports
- `.github/workflows/ci.yml`'s `backend-test` job only runs Postgres + Redis as service containers — there is NO MinIO service in CI. Any test exercising a `core/storage.py` code path must mock the storage call (`monkeypatch.setattr(<module>, "upload_file", fake_fn)` etc.) — never hit a real MinIO endpoint from a test, or CI will fail with connection errors. DB-touching tests are fine hitting real Postgres (CI provides it) via the existing `client` fixture / `psycopg2` cleanup pattern — see tests/test_dataset_routes.py
- NEVER call a second ad-hoc `asyncio.run(...)` against the real `core.database.engine`/AsyncSessionLocal from inside a pytest test function — `tests/conftest.py`'s `client` fixture is session-scoped and holds one event loop open for the *entire* test session; any other asyncio.run() that touches the same process-wide engine/pool will eventually crash with cross-loop asyncpg errors (`Event loop is closed`, `attached to a different loop`), even if you consolidate to one asyncio.run() per test or add engine.dispose(). The only safe ways to hit the real DB from a test: (a) go through the `client` fixture (HTTP calls into the app, which already shares its loop), or (b) for non-HTTP scripts, run them as a real `subprocess.run([sys.executable, "scripts/foo.py"], ...)` (a separate process/engine entirely) and verify results with sync `psycopg2` against `settings.DATABASE_URL_SYNC` — see tests/test_seed_data.py
- `training_engine/__init__.py` was deleted (PHASE1-WEEK3-002) — it was empty/unused (nothing imports `training_engine.*` anywhere) and its mere presence broke `uv run pytest tests/` there: pytest's rootdir package-walk treated `training_engine` itself as a subpackage and walked one level too far up to the monorepo root for `sys.path` insertion, so any `from <local_pkg> import ...` inside a test silently resolved against a same-named pip package instead of the local one. Do not recreate `training_engine/__init__.py` unless something actually needs `training_engine` to be an importable package — if that happens, also add explicit `pythonpath = ["."]` under `[tool.pytest.ini_options]` (no pyproject.toml exists in training_engine yet) so test imports keep resolving to the local subpackages first
